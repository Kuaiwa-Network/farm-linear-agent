# UI verification for the issue owner

Use this for appearance, sizing and adaptation changes. Keep the verification
proportional to the affected behavior; texture/export-only fixes do not require
redesigning an inherited panel. Follow repository instructions and the user's
actual scope. This introduces no separate UI task or human approval round.

## Establish the intended geometry

Identify whether an attached image is a reference or a bug screenshot from its
context; ask only if that distinction remains unresolved. Record its pixel size,
the game's logical design resolution and the scaling/offset between them.
Measure the panel bounds/origin, main art, section headings, rows, spacing and
buttons. Use the existing UIManager placement and scale rules when converting
these measurements. A component's editor canvas size is not its on-screen size.

Inspect shared components and natural art dimensions before changing containers.
Check loader fill and proportional scaling, percent versus fixed-delta relations,
list alignment with fewer items, clipping and states with missing/empty content.
Do not equate the presence of textures or text with the reference being restored.

## Check what the native publisher actually wrote

For layout/appearance work, run `publish-ui --packages PACKAGES_FILE` with
repeatable `--component PACKAGE/RESOURCE_ID` selections read from `package.xml`.
Select affected views and reusable/list item components, including components
whose URLs are assigned in code. The checker follows direct component references
in the selected packages. It does not infer dynamic URLs or every list template;
include these explicitly. Packages and dependencies retain their existing export
identity checks. Unselected historical components are not decoded or a reason
to broaden the repair.

Inspect `RUN/layout-check.json`. Unknown loader fill values, source/export size
differences and lost nested instance controller selections fail scoped export
validation; the staged assets and findings remain available for diagnosis.
For example, `scaleToFit` is not the reviewed native fill spelling: use `scale`
for proportional fit. A source declaration of a selected controller page is not
proof that the published instance uses it. Save valid selections with the native
editor and check the exported result. Do not patch generated bytes to hide a
source error. An omitted selection is recorded as `not_requested`, never passed.

The checker covers specific serialized facts. It does not execute controller
gears, relations, auto-size, transitions or business code, and cannot decide art
proportions or whether the intended page was selected by runtime code. Repository
previews remain approximate. Do not make an unknown fill mean proportional fit,
apply an unsupported controller override, or otherwise improve the preview beyond
what the native package implements.

## Verify the installed candidate in Unity

Use the reserved Unity instance and the final committed Client assets. Exercise
the actual view opening/binding/placement/SafeArea path. A fixture may supply test
data, but it must invoke those production paths; record any bypass as a limitation.
Direct package construction is useful for binding checks, not adaptation proof.

Cover the reference resolution, a supported tall aspect ratio, zero and nonzero
safe insets, and all relevant states that alter layout (for example enrolled and
not enrolled, empty/full lists, long text and selected tabs). Use the project's
supported device/inset fixtures, record the actual logical insets after conversion,
and include top/bottom and applicable side insets. Changing only the root height
does not exercise SafeArea. Reapply adaptation or reopen to check for drift.

Assert meaningful relationships: visible content and button hit bounds inside the
intended area, headings not overlapping controls, navigation above the scroll
region and stable relative positions after inset changes. Inspect the loader's
rendered content, not only its container dimensions; an unscaled texture can
overflow a correctly sized box. Do not "fix" tests by widening tolerances around
the current wrong layout or by hiding content.

Capture actual native runtime screenshots for the affected states. Compare them
with the reference at the same scale and aligned origin, using stable regions for
geometry and art. Account for changing data/animation rather than treating a
whole-image pixel difference as a verdict. Keep a concise report under
`state_dir/reports`: reference and candidate identity, resolution, inset/state
matrix, assertions, screenshot paths, observed differences and unresolved limits.
Do not label an approximate render as a runtime screenshot or infer visual success
from a passing test count. Reuse evidence only while its relevant inputs match.
